# Build and replay measurement

`CT_DEBUG_OPT` is an opt-in CMake cache option, off by default. It compiles `ct_ps2`, `ct_port` and `ct_host` with `-Og` while retaining `-g` in Debug. Tests keep their ordinary Debug flags; other configurations are unaffected. Leaving it off preserves unoptimized stepping and local-variable inspection.

After configuring a build, enable it with `cmake -S . -B port/build/windows-x64 -DCT_DEBUG_OPT=ON`; use the test build directory when measuring tests. Optimized builds also exercise naturally aligned native copies: `mgCDrawEnv::operator=` uses a complete `memcpy` through a native override rather than imposing a 16-byte alignment requirement on eight-byte-aligned host objects.

The per-unit pipeline strips overrides, applies native unit fixups and rewrites long64 in one Python process. Per-unit override lists limit invalidation to affected units; mirror headers are declared outputs so header changes rebuild dependents in one build. Unchanged generated bytes retain their timestamps.

Headless input startup applies shared input configuration and scripts without enumerating physical controllers, installing window-input hooks or capturing the mouse. Interactive startup uses the shared `InputInit`. No joystick-backend environment overrides are required.

For reproducible measurements:

1. Record configuration, compiler/dependency versions, optimization setting and compile job count.
2. Measure configure, clean build, no-op build, one unit edit, a common header edit and an override-set change separately.
3. Measure replay time with the same binary, input, frame limit and configuration, using a fresh save and pipeline cache per run.
4. Compare canonical images and exit status before treating an optimization as qualified. Test both optimized and unoptimized native alignment paths.
5. Use multiple trials and report median and spread. Record host load and distinguish process/container startup from compilation or rendering.

The [headless timing contract](headless-replays.md) explains mixer ownership. Unit timing and screenshot identity qualify their tested paths; they do not measure complete campaign behavior or interactive camera coverage.

## Windows launcher measurements

Measured on the working Windows checkout on 2026-10-14 with PowerShell 7.6.5, CMake 4.4, Ninja 1.13.2, llvm-mingw 20260922, Rust 1.99.0 and Corrosion 0.6.1. The configuration was `windows-x64` (Debug), `CT_DEBUG_OPT=OFF`, with 12 compile jobs. Timings below start inside PowerShell and exclude shell/process startup. Other work was active on the host, so these are diagnostic observations rather than an isolated benchmark or a before/after speedup claim.

| Work | Observed time | Work performed |
| --- | ---: | --- |
| First catch-up build | 128.6 s | 493 scheduled steps, including Rust GUI dependencies, generated units and C++ compilation |
| Settled direct builds | 2.54 s, 2.26 s | Cargo freshness check, Rust archive comparison/copy, runtime DLL comparison; no C++ compile or relink |
| Cached launcher build | 2.6 s | Dependency/cache checks plus the same settled build |
| `build.bat windows-x64` | 3.1 s | Same settled build through the public entry point |
| Controlled source timestamp update | 4.7 s | `identity.cpp` recompile and executable relink; a concurrent `mainloop.cpp` edit also rebuilt |

The first observation used the existing build tree; it was not a clean build. A separate configure catch-up took about 4.8 s. CMake's initial scheduled-step count can shrink after unchanged generated outputs are checked; it does not mean every listed unit will compile.

Ninja's log attributes about 1.0 s to the settled Cargo command and 0.9 s to Corrosion's subsequent comparison/copy of a 239 MiB static archive. Runtime DLL comparisons take about 0.6 s and overlap Cargo. Cargo reports 0.5–0.8 s internally. These checks retain Cargo dependency discovery and restoration of missing runtime DLLs. The measured settled cost does not justify bypassing them. No compile-job or optimization changes were made from these observations.

The launcher streams native stdout and stderr to the console and `build.log`, and prints the build duration and exit status. A delayed native fixture verifies that both streams arrive before completion, that more than 65 lines survive in the log, and that exits 0 and 23 propagate. The native process stays in PowerShell's foreground pipeline; interactive Ctrl+C was not exercised by the automated checks. PowerShell 7.0/7.1's redirected-stderr compatibility path is included, but execution was verified with 7.6.5. Release, clean-build and first-run dependency-download timings were not measured.

## Debug information size and link time

Measured on 2026-10-18 with llvm-mingw 20260922 (clang 23.1.2), Ninja 1.13.2 and 32 jobs, building `darkchronicle` in Release at `abe0d5d9`, before the crash handler and logger existed. Each link time is ninja's record for relinking after deleting the exe, with no compile. Other builds were running on the host, so link times are diagnostic.

| Configuration | `darkchronicle.exe` | PDB | Link (s) |
| --- | ---: | ---: | --- |
| Release, no `-g` (before) | 27,837,440 B | - | 0.57, 0.58, 0.77 |
| Release, `CT_SYMBOLS=embedded` (`-gline-tables-only`) | 61,396,992 B | - | 0.72, 0.72, 0.74, 0.75, 1.11 |
| Release, `CT_SYMBOLS=split` (adds `-gdwarf -gcodeview`, `--pdb`) | 54,619,136 B | 29,921,280 B | 0.63, 0.68, 0.68, 1.40, 2.08 |
| RelWithDebInfo (`windows-x64-release`, full `-g`), for comparison | 208,809,984 B | - | not measured |

Line tables add 33.6 MB to the Release exe. The DWARF sections grow from 4.2 MB (from linked libraries, none of it the game's) to 37.8 MB: `.debug_info` 14.3 MB, `.debug_str` 10.2 MB, `.debug_line` 8.3 MB, `.debug_ranges` 4.9 MB. With `--pdb`, lld moves the COFF symbol table into the PDB, so the split exe is 6.8 MB smaller. The extra link time from either mode is within run-to-run noise. Recompiling every C++ unit after the flag change took 120 s (`embedded`) and 105 s (`split`) on the loaded host. With the crash handler and logger linked in, a Release `embedded` exe of the working tree was 68,239,360 B.

## Incremental build invariants

- Only one ninja may write a build directory. Two concurrent builds interleave `.ninja_deps` records; ninja then drops every record after the damage on each load and, on Windows, never truncates the file, so every later build recompiles everything ("stored deps info out of date"). `tools/windows/build.ps1` holds `<build>/.kazarov-build.lock` for compilation and explicitly releases it before the game starts. `REPAIR_NINJA=1` runs `ninja -t recompact` to repair existing damage; normal builds leave the logs intact. Building a directory directly with `ninja`/`cmake --build` while another build runs bypasses the lock.
- Linking `kazarov_bridge` orders every compile of a target after the whole Cargo build. Only the port sources that include `kazarov_bridge/` or `rust/cxx.h` are compiled in `ct_port_bridge`; the rest of `ct_port` compiles alongside Cargo.
- The button glyphs and Windows runtime DLLs are copied by commands with declared outputs, so an up-to-date build runs neither.

## Windows build review, 2026-10-30

The Windows path is batch entry point, one PowerShell launcher, dependency validation, cached CMake configuration, parallel Ninja/Cargo build, current-data check, then executable launch. Astra reviewed the pipeline and prioritized dependency invalidation, Luau publication and recurring Ninja database rewrites. Compiler-result caching, ThinLTO caches, Cargo freshness checks and Docker's filtered build context remain enabled.

The previous dependency stamp hashed entire CMake files, so ordinary build-rule edits caused a Docker export and SDK extraction. The current stamp hashes acquisition declarations and recipes. FFmpeg contributes only the version, archive checksum, licence and configure flags consumed by the Windows Docker stage, so other platforms' host-helper changes do not invalidate Windows. A warm launch performs neither Docker inspection nor build/export. The one-time fingerprint migration in this checkout took 93 seconds for dependency refresh; cold acquisition and changed dependencies remain outside a few-second launch budget.

Native measurements in the existing Windows Release tree with 32 compile jobs found 1.81 seconds in unconditional Ninja recompaction and 2.50 seconds in the serial Luau prune/hash pass alone. Both recurring operations are removed. The Luau publisher owns a stamp and all script byproducts, so no-change builds perform no script scan, hash or copy. When inputs change, metadata identifies the required copies and worker threads copy/hash only those files. The ownership manifest is published after success, adopts the old hash manifest, and removes only unchanged obsolete owned copies. Installation retains its separate ownership manifest.

Publishing all 4,340 runtime scripts (47 MiB of source tree including declaration files) into a fresh temporary output took 7.38 seconds with 16 workers and atomic per-file publication. A single-worker trial under concurrent compilation took 51.53 seconds; host load was uncontrolled, so these observations are not an isolated speedup benchmark. Warm publication is skipped by Ninja rather than repeating either trial's work.

The cached public `run.bat --help` reached the launch stage in 4.2 seconds before the Cargo archive optimization, with dependency checking taking about 0.1 seconds and the data check about 0.1 seconds. The stage timer excludes PowerShell startup and executable initialization. This is a warm-tree observation under concurrent host work, not a clean-build measurement or a bound on game loading time.

Final validation used `run.bat --headless --frames 1`, including the public batch entry point's PowerShell startup. Two settled trials reached executable launch in 4.46 and 4.19 seconds; their internal launcher timers reported 3.2 and 3.1 seconds, and builds took 3.0 and 2.9 seconds. Both one-frame runs exited successfully. The first trial completed in 14.20 seconds including game initialization and rendering; the final warm trial completed in 5.73 seconds total. An intervening source edit rebuilt `menuaqua.cpp` and relinked, reaching launch in 11.39 seconds; it is excluded from the no-change observations. No settled trial invoked Docker, configured CMake, published Luau sources or relinked the game. Changed sources, first acquisition, extraction, lock waits and cold game initialization remain outside the few-second no-change build budget.

Windows Ninja builds link Cargo's archive directly using Corrosion 0.6.1's `ARCHIVE_OUTPUT_DIRECTORY` support. Its default artifact path includes the workspace name/path hash, target triple and Cargo profile. This removes a full archive comparison/copy on each run while retaining Cargo's complete dependency and environment checks. Custom Cargo profiles and other generators retain Corrosion's default behavior; an upgrade of Corrosion must preserve or revise the artifact-path mapping. The Windows configuration also caches `CT_WINDOWS_CARGO_HOME` and passes it directly to Cargo, so direct CMake builds and the launcher resolve registry sources from the same paths instead of invalidating Rust artifacts when their calling shells have different `CARGO_HOME` values.

Regression checks are `python -m unittest tools.luau.test_sync`, `pwsh -NoProfile -File tools/windows/test-dependencies.ps1` and `pwsh -NoProfile -File tools/windows/test-build.ps1`. The Luau checks include actual Ninja builds for no-op behavior, source edits, source additions/removals, deleted-copy restoration and downstream bytecode dependency ordering. The Windows fixtures check semantic dependency invalidation, archive-audit invalidation, shared data locks, streaming diagnostics, complete logs, native exit codes and build-lock release.
