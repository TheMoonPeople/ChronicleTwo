# mg_dataset guarded functions — pinned compiler, 2026-10-08

Measurements use integration `d7590de`, MWCC 3.0-011126, canonical `-O3,p`
flags, existing function pragmas, and the Satan’s Fiddle adapter. Whole-draft
word differences mask relocation operands; promotion additionally requires the
canonical complete-object byte and resolved-relocation check.

## Native MDS loader

`mgLoadMDSFile__FP10mgLoadData` is native. Its array allocation has a separate
`frame_count` rather than reusing the iteration index `i`. This naturally
separates the allocation-count and loop-index lifetimes; MWCC now reuses the
retail saved register for their non-overlapping values. The original draft’s
57/256 differing words were only the saved-register permutation:

`i s0→s5`, `object s1→s0`, `mds s2→s1`, `frames s3→s2`,
`current s4→s3`, `frame s5→s4` (retail → draft).

The corrected function has zero differing words: 0x3F4 code in a retail
0x400 padded extent. A source-local forward declaration makes the native
loader able to call the still-guarded `CreateFrameVisual` helper. The complete
unit has zero byte and resolved-relocation differences: 0x2840 bytes and 194
relocations. No shared-header edit or compiler-profile override is required.

A signed iteration index adds two code differences without correcting the
register permutation. Moving its declaration alone leaves the permutation
unchanged. Separate allocation and iteration variables express their distinct
roles and reproduce retail without a register-control directive.

The loader keeps three byte-offset expressions:
`(char *)mds + mds->object_ofs`, `(char *)object + object->size` and
`(char *)mds + current->mdt_ofs`. They walk the MDS file image itself. The
offsets and the variable record size are stored in the file
(`mg_dataset.hpp` `MDS_HEADER::object_ofs`, `MDTOBJ_HEADER::size` and
`MDTOBJ_HEADER::mdt_ofs`); they are not reconstructed field offsets. This is
the same serialized-format exception the matched collision loader uses
(`collision.cpp`: `header->vertex_ofs`, `material_ofs`, `faces_ofs`). A typed
`object++` stride would be wrong, because records are not a fixed
`sizeof(MDTOBJ_HEADER)` apart.

## Placement-new parks

|---|---:|
| `CopyFrameSub__FP8mgCFrameP9mgCMemoryiPP8mgCFrame` | 46/68 words; 0x108 / retail 0x110 |

| `CopyFrame__FP8mgCFrameP8mgCFrameP9mgCMemoryiPP8mgCFrame` | 1/208 words; 0x33C / retail 0x340 |
| `CreateFrameVisual__FP8mgCFrameP9mgCMemoryP9mgCMemoryP8mgCFrameP13MDTOBJ_HEADERP10MDT_HEADERiP17mgCTextureManagerPUiiPP8mgCFramePA4_A4_f` | 10/444 words; 0x6E8 / retail 0x6F0 |

`CopyFrame` (+0x138) and builder `End` (+0x144) each branch on `a0` after
placement new where retail branches on the equal-valued `v0`.
`CopyFrameSub` additionally shifts the frame-result copy around its null
branch; six allocations in `CreateFrameVisual` have the same family of branch
issue, with a separate four-instruction scheduling difference near +0x1E4.
These are placement-new parks; they need a general solution under this pinned
compiler, not assembly or manual constructors.

GPR helper masks 0, 0x10 and 0x30 yield identical initial unit drafts. No
floating literal is involved in the loader’s allocation-register permutation,
and no verified profile row is proposed.

## Nearmiss confirmation

A fresh pinned-profile raw-draft check reproduces End 1/96, CopyFrame 1/208
and CreateFrameVisual 10/444. End +0x144 and CopyFrame +0x138 each branch on
`a0` instead of the equal-valued placement-new result in `v0`; no other word
differs. CreateFrameVisual has six placement-new branches at +0x180, +0x30C,
+0x380, +0x414, +0x4C8 and +0x548, plus the four query-argument scheduling
words at +0x1E4..+0x1F0. These are confirmed parks; the query scheduling alone cannot
promote CreateFrameVisual.
