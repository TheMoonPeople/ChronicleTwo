`DngTreeMapInit__FP9mgCMemoryPiii` is now exact (0x3F8 bytes, GLOBAL, in
the 0x400 reservation). Two source corrections close its 55 words:

- **Opening modes are a switch.** Retail tests `li v0,3; beq s6,v0,sep;
  beqz s6,sep; b default`, an unoptimized two-target chain followed by an
  unconditional branch to the common-menu block. `if (mode == 3 || mode == 0)`
  inverts the last test (`bnez`), and every boolean form normalizes with

  `case 3: case 0:` tests zero first. The values are `MenuOpenType`

  the tree-map request; the in-dungeon main menu supplies its own type).

  `MenuCursorDataBuff` and reloads it for `LoadFileMenu` because the global
  is not `u_long128 *`: storing a converted `stGetTop()` result and passing

  other consumer, `CMenuTreeMap::InitEnd`, passes it to
  `EnterIMGFile(u_char *)`, so `u8 *` removes that cast. `void *` and
  `char *` also match; `u8 *` is retained for the IMG consumer. The earlier
  byte/void-global probes (71 words) combined these types with the boolean
  condition; with the switch they are exact. An assignment inside the
  loader argument does not reload.

`Init__6ClsMesFv` (retail binding 13) from the unchanged shared header, so

  `0 <= next_room_no`: a constant-left comparison emits `slt at, x, $zero`

### Route tables: function statics are not identifiable

Retail defines the route tables as LoadDngInfo's function statics
(`$2230`–`$2248`). The first trial declared them as typed `static` locals
at the top of the function, with the draft's uses renamed to the local names.
MWCC compiles them correctly but numbers them `$1522`–`$1540`; the unit's
counter is 708 behind retail at this function, accumulated in the preceding
code. The trial failed the PAL check: `.data` differs from `Table_2133`
onwards and `.sdata` from `dng_player_pos`.
Receipt: `.private/dngmenu-r0/load-build.log`.

The postprocessor renames a numbered local only through identity proofs, and
neither proof covers these tables:

- `name_initialized_locals` names nonpointer tables with a complete code
  consumer. The ten passage and four room point tables have no code
  reference; only the pointer tables point at them. `is_reverse_tbl`,
  `old_hokantbl_useno` and `is_reverse_tbl_room` are rejected because the
  consumer proof cannot resolve LoadDngInfo's references to the unnamed
  pointer tables.
- `pointer_table_names` accepts a pointer entry only when its target already
  has a retail name, or is an anonymous `.rodata` `at_` literal. Here the
  targets are named local `.data` tables.

Declaration order, `const` and section cannot close a 708-number gap, and
`const` would move the tables to `.rodata`, while retail keeps them in
`.data`/`.sdata`. The promotion commit therefore keeps the unit's convention
for retail function statics: file-scope `static` definitions with the retail
number in the name, as `RootTable_2119`, `name_tbl_2728` and
`medal_xytbl_1736` already do. The tables sit directly above LoadDngInfo,
their only user, and the draft's `__DATA` externs are gone.

A follow-up step leaves only the 14 point tables at file scope. The two
pointer tables and the three direction tables become real function statics
(`RootHokanTablePtrTable`, `RoomHokanTablePtrTable`, `is_reverse_tbl`,
`old_hokantbl_useno`, `is_reverse_tbl_room`). Once their point-table targets
have retail names, `pointer_table_names` proves the pointer tables, and the
complete LoadDngInfo consumer then proves the direction tables. All five take
their retail `$2240`–`$2248` identities. Full build OK and 149/149, with the
object unchanged (receipts `.private/dngmenu-r0/hybrid-{build,objects}.log`).
To make the point tables function statics as well, the postprocessor would
need a pass that names a numbered local `.data` table through a verified
pointer table's R_MIPS_32 entries. The pass would check family name, exact
declared size, exact bytes and no relocations. That is a toolchain change
outside this lane; no `scripts/build/` file is touched.
