### ResetAddress: exact only through a byte-pointer cast

The historical form `(char *)photo_work + index * 0x2000` (with or without
`(int)sizeof`) compiles to all 48 retail words. So does
`(char *)((void *)photo_work) + index * 0x2000`. The explicit conversion of
the decayed row-array pointer keeps `this + 0xD60` opaque: MWCC computes it
inside the loop, hoists it into each unrolled copy's preheader after the
induction setup, and recomputes it before the two-photo remainder (`+0x94`),
exactly as retail does. Every cast-free typed form folds `0xD60` into the
per-iteration offsets or computes the base once:

| Form | Result |
|---|---|
| `photo_work[i]`, `this->photo_work[i]`, `(*&photo_work)[i]`, `*(photo_work + i)` | 34/48 |
| `photo_work[0] + i * 0x2000`, `&photo_work[0][0] + i * 0x2000` | 34/48 |
| Casts after indexing (`(char *)photo_work[i]`, via `void *` or `u_char *`, `(char *)&photo_work[i]`) | 34/48 |
| Row pointer declared and assigned inside the loop body | 42/48 |
| Flat `char photo_work[30 * 0x2000]` (private header copy), `&photo_work[i * 0x2000]` or `photo_work + i * 0x2000` | 34/48; IsPhotoSpace, GetPhototWorkAdr and Initialize stay exact |
| `photo_work[0] + i * sizeof(photo_work[0])` | `0xB8`, undersized |

The retained 13-word row-pointer draft is therefore the best cast-free form.
An exact promotion requires accepting the byte-pointer cast; this is
recorded as a policy decision, not applied.

### MenuInventKey: card colour

`MenuInventKey__Fv` stays at **8/524**. Initializing card after the number-X
conversion still gives the documented ten-word a0/a1/a2 permutation in every
new loop form: `while`, card increment first (14), card declared at case
or function scope, `do`/`while` behind an `if`, renamed counter, nested block,
and `card = top + line` before (8) or after (10) the conversion. Testing the

The inventmn GPR helper mask changes only the `13.0f` constant temporary

production `0x30` row is already the best-scoring state; no mask reproduces
retail's `a2` card.

## Round 1 (nminv): CalcTex promoted

`CalcTex__11CMenuInventFv` is now exact with natural C++. It needs one
callee-scoped Satan's Fiddle row (`0x40490fdb`, `CalcMenuAdd__FPfff`; see
below). The guarded draft was 0x13B0 bytes, against retail's 0x13A0. It
had a 0x160 frame and a saved `s8`, against retail's 0x150 frame. The source
facts that close the gap:

- **Non-constant aggregate initialisers.** Retail's two zero templates
  (`at_3363` for the background position, `at_3379` for the clip range) are
  MWCC's templates for `int bg_pos[2] = {(int) left_top[0], (int) (left_top[1] - 480.0f)}`
  and `float clip[2] = {neta_board_form->y, neta_board_form->y + 6.0f + 270.0f}`.
  The compiler copies the template, then stores each element at a direct
  `off(sp)` address, as in screeneffect's `DepthOfField`. A copy from an
  extern `at_33xx` followed by element assignments makes MWCC keep element 1's
  address in a register: `v1` for the background and saved `s7` for the clip
  bottom. The clip case caused the extra saved register and the 16-byte
  larger frame. At promotion the two `INCLUDE_BSS` placeholders anchor the templates;
  the later data migration removes both markers and retains the naturally
  emitted templates.
- **The clip range is a `float[2]`.** A `NetaClipRange` record built by the
  same initialiser still keeps `&clip.bottom` in `s7`. The array form does
  not. The record type is removed because nothing else uses it.
- **`SetPos` stores the background position.** Writing `bg_form->x` and
  `bg_form->y` separately reloads `this->bg_form` after the first store;
  retail's inline `CMenuPosDataForm::SetPos` loads it once.
- **The memo bar step divides 216.0f** (`0x43580000`), not 108.0f.
- **The album scroll target is computed before `bar_y` is copied.** `bar_y`
  is address-taken (`CalcMenu1` writes it), so its store orders every later
  load through `frame`, `bar` and `this`. Retail loads all the scroll
  operands before that store. The division is held in its own local
  (`scroll_step`), like the card and memo `bar_step`. MWCC then emits it as the
  multiply's first operand, as retail does. Writing it inline gives
  `album_top` first, whatever the source operand order.
- **Card bar declaration order.** `bar_step = 0.0f` is declared after
  `knob` and `hidden`. With it first, `card_max - 5` is allocated to `a0`
  instead of retail's `v1`.
- **The blink sine is its own statement** (`wave`). With the sine inline in
  `128.0f + 64.0f * sinf(...)`, the 128.0f temporary that is also stored to
  `neta_color[2]` takes `v0`. Retail has 64.0f in `v0` and 128.0f in `v1`.

### SF row: pi before pi/22 for CalcMenuAdd

`CalcMenuAdd(&effect_bob_angle, 3.1415927f / 22.0f, 3.1415927f)` is the only
remaining difference with the natural source. Retail materialises the third
argument's pi (`lui v1,0x4049`/`ori`/`mtc1 $f13`) before the second's pi/22
(`0x3e123a14`). The source materialises pi/22 first. The call opens the block
at 0xFC8, so no earlier instruction competes. This is the documented binary32
pi evaluate-first state (cf. `pbuggy.cpp` `InitBomb`). The row is scoped to
`CalcMenuAdd__FPfff` with `expected_matches: 1`, because CalcTex has 11 other
pi constants. Unscoped evaluate-first rows for 64.0f, 128.0f and 20.0f do not
change the function and are not used. With the row, the full build verifies
SCES_511.90, all 149 units pass `check_objects`, and the report shows 6760
perfect.
