# October 8 night (nmquad): KeyStep frame-slot order

Base `c75b0713`, image `chronicletwo_dev:sf-63f7a9e`, canonical MWCC

`0x1A70`); every difference is the frame size or a stack offset shifted by

## How MWCC orders memory-resident locals

Toy compiles with the canonical options (`.private/nmquad/toy/t1..t4`) and
probes on the draft establish the frame rule for address-taken or
variably-indexed locals:

- Slots group by size class. Arrays of 16 bytes or more sit lowest, each
  16-byte aligned; 8-byte objects (`int[2]`, `float[2]`, a two-`int` struct)
  follow, 8-byte aligned; 4-byte objects (`int[1]`, `char *[1]`) are highest.
  A 12-byte `int[3]` was placed above an 8-byte pair in one toy and below it
  in another, so its class is not established.
- Within a class, addresses ascend in declaration order, whatever the
  scope (function body or nested block) or first-use order.
- A variably-indexed array is addressed through an index register, so its
  accesses carry no `sp` offset. Retail's and the draft's `rowInfo[13]` at
  `+0xE0` is stored and reloaded once per refresh row through
  `addu v0,s2,sp; addiu a0,v0,0xE0`. That is retail KeyStep's only indexed
  stack address. Resizing `rowInfo` to 30 entries moves `formPos` to `+0x160`
  and every 8-byte block array to its retail offset (11 words, only
  `formPos` wrong).

KeyStep's 8-byte class is therefore `formPos` (`+0x120`), then the two
quest-fish `values` pairs, `listPos`, `scrollRange`; the 4-byte class holds
the refresh-loop `title`, `itemNo`, `slotNumber` and `slotWidth` arrays at
`+0x188..+0x19F`. This explains why the refresh-loop arrays sit above the
later-declared `listPos` and `scrollRange`.

## Consequence for the 64-byte interval

Retail's unaccessed `+0x128..+0x167` (no `sp` offset and no indexed address
reaches it) lies inside the 8-byte class, between
`formPos` and the first `values` pair. Only two layouts reproduce it:

1. `formPos` is a 16-byte-class array of 57 to 72 bytes whose first pair is
   used (the excluded nine-pair array: `0x168 - 72 = 0x120`, 16-aligned), or
2. 64 bytes of 8-byte-class objects (pairs or two-`int` structs; possibly
   12-byte arrays) declared after `formPos` and before the quest-fish
   block, none of whose accesses survive. No toy has produced such a slot:
   unreferenced or store-only locals get none (round 2), and indexed
   accesses stay visible.

A single 64-byte array cannot produce it: it would be 16-byte class and sit
below `formPos`. A second per-row array in the `rowInfo` style
(`CDC2Mes *rowMesList[13]`, declared after `formPos`) confirms this: it is
placed below `formPos`, gives the retail frame but moves `formPos` to `+0x160`
and changes the refresh-loop allocation (210 words, body `0x1A6C`).
Neither layout has an evidenced owner in retail's accesses, so no storage is
added and the guard stays.

## Owners ruled out

- Dead initialised pairs: retail's `values` and `listPos` pairs copy 8-byte
  templates (`ld`/`sd`), and `scrollRange` has its own. menuop's `.sdata`
  holds exactly the referenced templates (`at_2335__3` = {76, 164},
  `at_2342` = {6, 250}) and no unreferenced pair, so no initialised local
  was optimised away.
- Inlined helper locals: `GetSaveMenuCard` is inlined nine times, eight of
  them before the refresh block, which would match 8 x 8 bytes. A toy with
  an inlined helper holding a two-pointer array (`.private/nmquad/toy/k1`,
  `k2`) gives one slot per expansion, but after all of the caller's own
  8-byte locals, including later block-scoped ones, and the helper's
  stores and loads remain. Inline-expansion storage therefore cannot sit
  between `formPos` and `values`.
- Caller locals handed to inline helpers: a pair filled through a pointer
  parameter, two scalars or two elements bound to reference parameters
  (`.private/nmquad/toy/k4`) are promoted to registers and get no slot. A
  struct returned by an inline helper keeps visible `ld`/`sd` copies.

No compiled form gives an object a slot with no surviving access. Every
retail access below `values` is to `+0x120`/`+0x124`. So the interval is
most plausibly the unused tail of one 16-byte-class aggregate at `+0x120`.
Diagnostic `int formPos[15]` to `int formPos[18]` (60 to 72 bytes) all give
**0/1692**. `[19]` and `[20]` give 24 words again (`.private/nmquad/mop/fp*`),
consistent with the 57 to 72 bytes above. The nine-pair `int [9][2]` is one
such shape. Choosing a size without an access that shows it is the policy
question already on record.
