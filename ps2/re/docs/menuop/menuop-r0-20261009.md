## Guarded KeyStep hygiene

The cleanup preserves the guard, the two-integer coordinate scratch buffer,
the declaration order, and the control-flow forms established in
[round 3](round3-20261008.md) and [nmquad](nmquad-20261008.md).
Automatic locals use snake case. The function-local statics retain their
retail names `FormatCase` and `DarkClonicleFileMax`.

Existing enums name the direction and shoulder bits, face-button dispatch,
base opening/closing modes, cancel sound, message presets, card-size requests,
memory-card completion/error values, and dungeon loop. The PS2 card type uses
the SDK's `sceMcTypePS2`, already included through `memcard.hpp`.
The completion sound `0x1F` has no existing enum and remains numeric.

The owned header adds these source-compatible values without changing any
class layout or existing signature:

- `SaveMenuStep`: zero waits for opening to finish or permits slot selection;
  one waits for the chapter-eight notice or the exit confirmation. These
  values describe base `step`, rather than the manual menu's `key_arg_no`.
- `SaveMenuEndCode`: ten reports successful game or fish-data loading through
  `MenuArg.end_code`. Existing native title and fish-race consumers distinguish
  that result from leaving the save menu without loading.
- `SaveFileKind`: zero overwrites a complete file; one creates a new file and
  its directory. `EnvSetSave` and the save-selection branches establish these
  two operations.
- `SAVE_MENU_PAGE_NONE`: minus one means no page transition is pending.

`YesNoCursor2` returns `MesYesNoResult`, while `YesNoCursor` returns the
zero-based cursor position. Only the former's confirmed outcomes use
`MES_YESNO_YES` and `MES_YESNO_NO`. The qualified base `ClsMes::mes_no` reset,
logical negation for the opposite slot, shared transfer snapshot and deliberate
confirm/cancel fallthrough retain their documented meaning.

### Real storage and initialization

The thirteen-entry `row_info` array is explicit retail storage at stack
`+0xE0`, addressed as `sp + row * 4 + 0xE0`. Retail stores the current file
pointer into that row and reloads it before building the row's location,
chapter and number messages. It is retained with its existing extent.
The manager pointer is one snapshot used for five loaded-result fields;
the transfer count is one snapshot used by each of four progress updates.
Neither is an unused scalar or a single-use copy wrapper.

The local `DarkClonicleFileMax` has no subsequent read, but retail executes
its one-time initialization at KeyStep `+0x24C..+0x260`. Its four-byte object
and one-byte guard therefore remain. The two zero-initialized message pairs,
one-element message/title arrays, and list-origin pair also have real retail
aggregate copies. Their initializers and array shapes remain intact.
No raw pointer arithmetic, type pun, goto, inline assembly, named literal
stand-in, artificial helper or dummy scalar is present in the cleaned draft.

## Position-array decision and native promotion

The night-run brief accepts `int form_pos[9][2]` as the position-pair array
and requires the promotion to be independently droppable. Its first pair
occupies stack `+0x120..+0x127`; the eight unused pairs occupy
`+0x128..+0x167`. This moves the later quest/space message pairs, list origin,
scrollbar range and one-element message arrays to their retail offsets and
restores the retail `0x1A0` frame.

The existing manual/option draws use the same pair-array idiom and reuse
their first pair for `GetPutPosXY`. [Nmquad's measurements](nmquad-20261008.md)
show that any aggregate size from 60 through 72 bytes reproduces the frame;
76 or 80 bytes does not. Retail accesses establish the first pair and the
reserved interval, but do not independently identify the original array's
element count. Nine pairs are the accepted source-shape decision, rather than
a newly discovered retail extent. No unrelated storage is enlarged. Nine pairs
occupy exactly 72 bytes, filling `+0x120..+0x167` with no alignment slack;
shorter matching aggregates fill the same interval only through padding.

The four form-coordinate call pairs use `form_pos[0][0]` and
`form_pos[0][1]`. The KeyStep guard and its assembly fallback are removed
manually, preserving the separate `MenuManualInit` guard and source.
No data marker is removed in the promotion step.
