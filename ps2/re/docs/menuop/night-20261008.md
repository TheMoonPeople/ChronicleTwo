## Round 2 — stack-interval evidence (no source change)

Base `750320ef`. KeyStep stays guarded at 24/1692; every remaining word
is the `0x40` interval at retail `+0x128..+0x167` (frame `0x1A0` vs `0x160`).
The unused nine-pair coordinate array is excluded by the round-2 brief, so no
storage is added. New compiler facts narrow what can own the interval
(toy compiles in `.private/nmmenu-r2/toy/toy3.cpp`, `toy4.cpp`):

- MWCC allocates **no** stack for a local array that is never referenced,
  one referenced only inside `if (0)`, one only stored to, or one inside an
  inlined function whose loop runs zero times. An unreferenced
  leftover declaration therefore cannot explain the interval.
- A constant-indexed local array promoted to registers (including a
  sixteen-element `int` array) also leaves no stack slot.
- The interval therefore belongs to an aggregate that is resident in memory
  (address taken) of which only part is accessed. The `formPos` pair is the
  only address-taken aggregate adjacent to it, which is why the earlier
  nine-pair diagnostic gives 0.

Upstream precedent for that shape exists in matched code:
`CRemovalMenu::KeyStep` (editmenu) declares `int line_pos[12][2]`, fills
nine pairs and passes `&line_pos[0][0]` with count 9 to `SetMsgItemPos`. It
reports no use of the last three pairs. Whether KeyStep's position pair was
declared the same way is a coordinator decision; it is recorded here only.

A further toy (`.private/nmmenu-r2/toy/toy5.cpp`) tests locals referenced only
from unreachable code: an array after a `return` inside a branch, after a
`break` inside a `case`, after the function's final `return`, and under a
`const int` zero condition. None receives a stack slot; the larger frames in
the first two cases come only from saved `s` registers. Leftover dead code
therefore does not explain the `0x40` interval either.
