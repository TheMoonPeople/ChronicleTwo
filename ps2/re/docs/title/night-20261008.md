## TitleModeKey — promoted with control rows

`TitleModeKey__Fv` matches (0/624, raw `0x9BC` in retail extent `0x9C0`) with
the five `CalcMenuAdd__FPfff` control rows of
[selector-context-20261008.md](selector-context-20261008.md), now committed in
`scripts/build/satansfiddle.json` (with their `expected_matches`). The whole
title unit passes.

The memory-card snapshot keeps the card pointers and the inserted-port bytes
in two-element arrays, as the matched `TitleMCCheckKey` in this unit does
(`MC_CARD_INFO *cards[2]`, `u8 inserted[2]`):

```cpp
MC_CARD_INFO       *cards[2];
u8                  inport[2];
cards[0] = &card_manager->card[0];
cards[1] = &card_manager->card[1];
inport[0] = TitleMCCheckInport[0];
inport[1] = TitleMCCheckInport[1];
```

MWCC keeps the constant-indexed elements in registers, but colours them
differently from separate scalars: `inport[1]` takes `s1`, `inport[0]` `s2`,
`cards[0]` `s3` and `cards[1]` `s0`, with both narrowing `andi`s in place, as
in retail. The card pointers are assigned before the port bytes; all six
declaration orders of `card_manager`, `cards` and `inport` give 0 with that
assignment order and 6 with the ports assigned first (`tk-b*`). A port array
alone with scalar card pointers gives 13 (`tk-a3`: the ports flip but the
card pointers move to `s2`/`s3`).

The four two-argument fade calls pass their zero limit explicitly
(`CalcMenuAdd(&TitleInfo->menu_alpha, float(-12.0), 0.0f)`); the former
file-local redeclaration with a default argument is removed, and the function
uses the `menucommon.hpp` declaration. The explicit and default forms compile
identically and satisfy the same row counts.

Validation: `.private/nm/receipts/titlekey-build.log` (`SCES_511.90: OK`,
6,756 perfect, 116 asm), `titlekey-objects.log` (149/149; only `menusys.cpp.o`
and `title.cpp.o` differ from the upbase build), `titlekey-hashes.txt`.

Retail holds `inport0` in `s2` and `inport1` in `s1`; MWCC reverses them. The

  `inport0` and `inport1` (`tk-p*`): best 5 (15 orders), otherwise 8, 9, 12
  or 13.
- The four snapshot locals declared at function entry, in all 24 orders
  either before (`tk-fr*`) or after (`tk-fo*`) the existing entry locals:
  best 5, otherwise 8, 9, 12 or 13.
- A two-byte `inport[2]` array: filled by a loop 561, aggregate-initialized
  614, two element assignments after the card pointers 13.
- Diagnostic only, not source candidates: an extra `!= 7` use of either port
  (507, 515) changes the block's schedule rather than only its colouring.
- All 23 other orders of the four snapshot assignments (`tk-as*`): the loads
  follow the written order, but `TitleMCCheckInport[0]` always lands in `s1`
  and `[1]` in `s2`. Orders that assign `inport1` first report 3 masked words
  only because the probe masks relocation addends; the loads then fetch the
  other element into each register, which the object check rejects.

Toy compiles (`.private/nm/ds/t7`–`t10`, neutral translation unit) reproduce
the native allocation exactly: `card1` `s0`, `inport0` `s1`, `inport1` `s2`,
`card0` `s3`, with the second port's `andi` written to `s1`. Integer
snapshots instead follow declaration order. Neither declaration order,
assignment order, a combined declaration, `==`/`else` or `!=` tests, a `bool`
lost flag, explicit `(int)` casts, a reordered flag assignment, nor snapshots
placed after the `TitleMCCheckNow` return (MWCC does not hoist them above that
branch) gives the second port the lower register. Changing use counts, range
lengths or test order moves both ports (`s2`/`s0`, `s0`/`s3` and similar), and
named call results move the `andi` after each call (`s4`/`s0`), so the choice
follows the ports' uses and live ranges rather than their declaration or
numbering. Retail's `inport1` `s1` / `inport0` `s2`
(both `andi` in place) therefore needs a different use structure that has not
been identified.

With scalar snapshots no form exchanges the two port registers without
disturbing the rest of the block. `TitleBootInit` was not attempted; it is the placement-new blocker
recorded in [notes.md](notes.md).

## Round 1b — retained TitleBootInit improvement

evidence and are not repeated. Existing m2c output is
`title-analysis/TitleBootInit.m2c.txt`.

The guarded draft improves from **56/676 to 30/676** without new SF rows:

- Declare the LOCAL TitleBootInit as `static`.
- Use signed `int` file-size outputs, matching LoadFile2's declaration, and
  a separate scoped logo size. Retail passes stack `+0x2DC` for that size
  and `+0x2D8` for subsequent loads; the prior shared local conflated them.

## Round 2 — TitleBootInit guarded draft 27 → 10

Base `750320ef`, image `chronicletwo_dev:sf-63f7a9e`, production SF profile.
The guarded draft improves from **27/676 to 10/676** with no profile row; the
private full-wrapper unit check (`.private/nmmenu-r2/title/tb-r2-retained2-full/`)
keeps the `0xA84` body, reports equal relocation offsets, and fails only
TitleBootInit's bytes. Three source facts:

- **Map-buffer top (2 words).** Retail computes the `stSetBuffer` argument
  straight into `a1` and copies it to `s1` in the delay slot. The map top
  is read twice: `u_long128 *map_top = DataBuffer.stGetTop();` followed by
  `TitleMapBuffer.stSetBuffer(DataBuffer.stGetTop(), 0x40000);`. MWCC merges
  the two inline reads into one value, now coalesced with `a1`. An
  assignment inside the argument, or passing `map_top`, computes into `s1`
  and copies to `a1` (23). `u8 *`, `u_int *` and `void *` map-top locals
  with casts, inside or outside the argument, also stay at 23.
- **Menu argument order (7 words; relocation offsets realign).** The
  assignments are `mes_tex_block`, `scene`, `tex_block_top`,
  `tex_block_num`, `pack`. All 120 orders were compiled
  (`.private/nmmenu-r2/gen/tmopart.*.out`; digits index the former order
  mes/top/num/scene/pack). Seven give 14: 03124, 03142, 03412, 30124, 30142,
  30412 and 34012, i.e. `mes_tex_block` and `scene` before `tex_block_top`
  before `tex_block_num`, with `pack` not ahead of both of the first two
  (04312, 40312 and 43012 give 30). The retained order keeps the other
  fields in their former order.
- **Icon loop indexes the table directly (8 words).** The loop writes
  `MC_ICON_Data[i].name`, `&MC_ICON_Data[i].size`, `.data` and `.size`
  directly, with no icon or size pointer:
  `memcpy(MC_ICON_Data[i].data, icon_file, MC_ICON_Data[i].size)`. The row
  address is then a CSE temporary, coloured after the loop offset, and MWCC
  keeps `&MC_ICON_Data[i].size` from the call in `s4` for the copy count,
  computing it again after the call as retail does: offset `s2`, row `s3`,
  size address `s4`, file `s5`. The scope of `i` and `icon_file` no longer
  matters (four placements, all equal). The former named `icon`/`size`
  pointers give 14–27 in every placement and access mix tried (80 scope
  combinations `tg-*`/`tu-*`, 160 access mixes `tw-*`, references, size
  assignment inside the Alloc argument); keeping a named size pointer with
  the indexed row merges the two size-address computations and drops an
  instruction (`0xA7C`, 334).

### Remaining residual (10)

- Camera constructor floats (6 words): the recorded private zero
  evaluate-first row for `__ct__15mgCCameraFollowFffff` removes them; it
  remains uncommitted because the function stays guarded.
- `memcpy` argument loads (2 words, `+0x574/+0x578`): retail loads the
  destination (`a0`) before the count (`a2`). Toy compiles
  (`.private/nmmenu-r2/toy/`) show MWCC evaluates the count first when the
  destination is already `void *` and only the count needs a conversion (int
  to `size_t`); any non-`void *` destination field (`u_int *`, `u_long128 *`)
  restores retail's order. `SetMCIconData` (menuop) assigns `GetPackFile`'s
  `u_int *` straight into `data` and memcard casts it to `char *`, so
  `u_int *data` fits every user. memcard.hpp is not owned by this lane: the
  proposal is `.private/proposals/memcard-icon-data-u_int.patch`, with the
  title assignment then written `(u_int *) DataBuffer.Alloc(…)`. Count casts,
  `void *`/`const void *` file pointers, a named destination local and an
  explicit `(void *)` Alloc cast leave the order unchanged.
- The placement-construction branch at `+0x7D8/+0x7DC` (2 words) is exactly
  the global placement-new null-check shape and is left to that lane.

With the header proposal applied privately and the zero row, the
full-wrapper title unit fails only at `+0x7D8/+0x7DC` (2/676, `0x68A8`
bytes, 2,265 relocations, `.private/nmmenu-r2/title/tb-r2-u32-zero-full/`).
The proposed field type leaves the other users byte-identical: private
full-wrapper compiles of menuop (`0x7DE4` bytes, 2,075 relocations) and
memcard (`0x475E` bytes, 515 relocations) with the shadowed header pass
with no problems (`.private/nmmenu-r2/{menuop,memcard}/hdr-u32-*/`).
Once the placement-new lane solves that shape, the function needs the
header change, the zero row (as a callee-scoped selector with
`expected_matches: 1`) and guard removal.
